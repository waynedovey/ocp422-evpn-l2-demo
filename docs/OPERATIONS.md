# Operations and troubleshooting

This file records the actual lab path. The cluster hosts and gateway ports are **specific to these RHPDS workshops**. Ask permission before changing SSH server settings; never bind new public services to the shared SSH gateway.

## Start the inter-bastion SSH tunnel

The source is **Bastion A**, not the Mac. The RHPDS gateway only forwards the published SSH service, not a general-purpose IPSec/VXLAN port. The two sites have duplicate private node networks and need unique routed VTEP addresses.

Bastion B administrator (if workshop policy permits):

```bash
printf 'PermitTunnel point-to-point\n' | sudo tee /etc/ssh/sshd_config.d/04-evpn-lab.conf
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T | grep '^permittunnel '
sudo systemctl reload sshd
sudo ip tuntap add dev tun7 mode tun user lab-user  # ONLY if absent
```

Generate an A-local SSH key with `ssh-keygen` only if one doesn't exist, copy **only the public key** to Bastion B with `ssh-copy-id -p 31156 lab-user@ssh.ocpv08.rhdp.net`. There was a broken preexisting IdentityFile reference on Bastion A; avoid it by using `ssh -F /dev/null -i ~/.ssh/id_rsa -o IdentitiesOnly=yes`. Confirm this direct **A→B** connection works in batch mode before tunnelling. Verify the remote host fingerprint out of band; never set `StrictHostKeyChecking=no`.

On the Mac: `./scripts/05-start-tunnel.sh start`. The script creates/assigns `tun7` on both bastions, starts `ssh -f -N -T -w 7:7` **from A**, then pings each end. It does **not** alter `sshd` or distribute SSH keys. If a stale SSH tunnel process exists but no traffic passes, inspect it before restarting rather than stacking competing `ssh -w` sessions.

## FRR setup and checks

For the proven topology:

| Peer | AS | Transport |
|---|---:|---|
| OCP Site A nodes → Bastion A `10.10.10.1` | 65001 → 65000 | local `eth1` |
| OCP Site B nodes → Bastion B `10.10.10.1` | 65002 → 65000 | local `eth1` |
| Bastion A `10.254.254.1` ↔ Bastion B `10.254.254.2` | 65000 ↔ 65000 | SSH TUN `tun7` |

`fabric/site-a-frr.conf` and `site-b-frr.conf` exactly match the accepted FRR 8.5 templates generated by `06-complete-fabric.sh`. Run **`frr-check`** before `fabric`. In FRR 8.5, keep `send-community` and `attribute-unchanged next-hop` at BGP neighbor scope, and only the EVPN neighbor `activate` directives inside the EVPN address-family block. Earlier revisions failed validation at `exit-address-family`; these corrected configurations were successfully parsed on both bastions. Never hand-edit controller-generated `ovnk-generated-*` FRRConfiguration CRs.

Established BGP peers display a **numeric** `State/PfxRcd` value, e.g. `0` or `13`:

```bash
ssh -n -p 31482 lab-user@ssh.ocpv02.rhdp.net 'sudo vtysh -c "show bgp l2vpn evpn summary" -c "show bgp l2vpn evpn"'
ssh -n -p 31156 lab-user@ssh.ocpv08.rhdp.net 'sudo vtysh -c "show bgp l2vpn evpn summary" -c "show bgp l2vpn evpn"'
```

After switching, both bastions reported 7 dynamic local OpenShift neighbors plus 1 inter-bastion neighbor, 14 type-3 routes, and each VM-host FRR reported 13 remote/local-other VTEPs. MAC type-2 routes are learned following guest traffic; inspect them again **after** the guest ping.

## Routing and forwarding

The `fabric` stage creates explicit `10.251.10/24` and `10.251.20/24` static routes via `tun7`, local per-node `/32` routes via the worker or control plane node's **real local underlay address**, and narrowly scoped `nftables` forwarding exceptions between `eth1` and `tun7`. There is no `firewall-cmd` on these particular bastions; their nftables `inet filter forward` chain has a default `drop` policy.

- Inbound `eth1` → `tun7`: local site's VTEP `/24` to remote site's VTEP `/24`.
- Inbound `tun7` → `eth1`: the reverse.
- Bastion A and B retain their independent, overlapping `10.10.10.0/24` networks; **never** bridge or route that entire prefix across the tunnel.
- Each OpenShift node has a temporary route to the **other site's** VTEP `/24` via local `10.10.10.1` on `br-ex`. This is only a workshop shortcut; it requires reapplication after a node reboot.

A read-only packet trace if forwarding stops:

```bash
sudo tcpdump -nni eth1 'host 10.251.10.15 or host 10.251.20.24'
sudo tcpdump -nni tun7 'host 10.251.10.15 or host 10.251.20.24'
sudo nft -a list chain inet filter forward
```

If packets enter `eth1` but don't leave `tun7`, first check the nftables forward chain and matching rule counters. The lab hit exactly that blocker and solved it using scoped rules instead of globally disabling the firewall.

## Validation

```bash
./scripts/04-test.sh --full
virtctl --context="$SITE_A_CONTEXT" -n evpn-demo console vm-site-a
# in guest: ping -c 4 10.250.50.4 && ip neigh show 10.250.50.4
./scripts/04-test.sh --strict
```

For a **new** deployment, do not hard-code `.4` until you query the newly assigned Site B VMI IP; each workshop CUDN has an independent DHCP/IPAM context. Resolve overlapping guest assignments before claiming successful L2 adjacency.
